# Securely connecting your own devices (phone, home PC, laptop, VPS) without open ports, for end-to-end encrypted offloading of AI jobs

Scope note: research as of 2026-11-08. Claims marked **[verified]** were checked against the fetched page or search results in this session. Claims marked **[bg]** come from background knowledge and point to the canonical official URL, but that page was **not** re-fetched in this session. The report writer should treat [bg] items as well-established but not freshly verified for 2026. Some search-result summaries came from aggregator blogs; where that applies it is stated.

## Q1: Connectivity options compared (NAT traversal, relay fallback, licenses, mobile support, battery)

### Takeaway
All serious options follow the same pattern: an outbound connection to a coordination or relay server, then UDP hole punching for a direct path, with a relay as fallback. The relay sees only ciphertext. Hole punching alone succeeds in roughly 70–90% of cases (libp2p measured about 70%; Tailscale estimates over 90% for basic techniques; iroh reports about 95% of bytes going direct). A relay fallback is therefore mandatory. For a 2-person team running Node.js runners, the cheapest robust options are: (a) Tailscale or Headscale as a network layer underneath the existing design, or (b) keep the existing outbound WebSocket relay through your own server and add application-layer E2E encryption. iroh (1.0 since June 2026, with Node.js/Swift/Kotlin bindings) is the strongest library option if direct P2P inside the app is wanted.

### Cited Findings

**How NAT traversal works in general (Tailscale's reference article)**
- Packets have to flow out before replies can flow back in. Behind two stateful firewalls, both peers must send at about the same time. STUN tells a device its public ip:port, and the STUN request must use the same socket as the later data traffic. — [Tailscale: How NAT traversal works](https://tailscale.com/blog/how-nat-traversal-works) [verified]
- "Easy" NATs (endpoint-independent mapping) keep the same public port for every destination. "Hard" NATs (endpoint-dependent) map each destination to a new port. With one hard NAT side, about 1,024 random probes give roughly 98% odds of success. With hard NAT on both sides, reaching 99.9% takes about 170,000 probes per side (about 28 minutes at 100 packets/s), which is not practical. — [Tailscale](https://tailscale.com/blog/how-nat-traversal-works) [verified]
- Typical failure cases are hard NAT on both sides (corporate and cloud NAT gateways), CGNAT without hairpinning, networks that block outbound UDP (e.g. guest Wi-Fi that only passes DNS), and missing or broken UPnP/NAT-PMP/PCP. — [Tailscale](https://tailscale.com/blog/how-nat-traversal-works) [verified]
- Tailscale estimates that STUN plus simultaneous sending yields a direct connection "over 90% of the time". Otherwise DERP is used: a relay over HTTP(S) that forwards already-encrypted packets by public key and also serves as the side channel for setting up the direct path. Tailscale picks paths ICE-style, trying them in parallel, and since v0.100.0 has chosen by measured latency. — [Tailscale](https://tailscale.com/blog/how-nat-traversal-works) [verified]

**Measured hole-punching success rates (libp2p/DCUtR)**
- Trautwein et al. (IMC '26, arXiv 2604.12484 / 2510.27500): more than 4.4 million traversal attempts from over 85,000 networks in 167 countries. The conditional hole-punching success rate is **70% ± 7.1%**, provided relay reservation and address discovery succeeded. TCP and QUIC perform statistically the same. 97.6% of successful connections succeed on the first attempt. — [arXiv 2510.27500](https://arxiv.org/html/2510.27500v1); [ProbeLab IMC '26](https://probelab.io/publications/large-scale-measurement-of-nat-traversal-for-the-decentralized-web-a-case-study-of-dcutr-in-ipfs/) [verified via search snippet]
- ProbeLab follow-up: for port-restricted cone NAT, the dominant class, the rate is 82.9% (3,669 of 5,215 peers). — [ProbeLab: Can libp2p punch through NATs?](https://probelab.io/blog/can-libp2p-punch-through-nats/) [verified via search snippet]
- Earlier: about 72% from a single home client (2022 talk), and about 80% for Go clients versus lower rates for Rust and VPN clients. — [ProbeLab talk](https://probelab.io/talks/libp2p-nat-hole-punching-success-rate/); [IPFS Camp talk](https://probelab.io/talks/decentralized-nat-hole-punching/) [verified via search snippet]

**Option profiles**

- **WireGuard (plain)**: kernel/userspace VPN built on the Noise IK handshake (Curve25519, ChaCha20-Poly1305, BLAKE2s), with static keys and no built-in NAT traversal or discovery. At least one peer needs a reachable UDP port, which in practice means a VPS as hub, with `PersistentKeepalive` to keep NAT mappings alive. Kernel module is GPLv2; official apps exist for Android and iOS. — [WireGuard protocol](https://www.wireguard.com/protocol/); [WireGuard quickstart](https://www.wireguard.com/quickstart/) [bg]
  - Inference: hub-and-spoke through your own VPS (UDP port open on the VPS only, not at home) is the simplest zero-vendor variant. All traffic goes through the VPS, which sees only WireGuard ciphertext.
- **Tailscale**: WireGuard plus a coordination server plus DERP relays, with the NAT traversal described above. [verified, see above] The client code is open source (BSD-3) and the coordination server is proprietary. — [github.com/tailscale/tailscale](https://github.com/tailscale/tailscale) [bg]
  - Free Personal plan: according to the official docs page (validated 2026-04-08), **6 users** per tailnet with unlimited user devices. Tagged devices are reportedly capped at 50. Some third-party sites still list the older "3 users / 100 devices". Personal is intended for non-commercial use; Standard is about $8/user/month and Premium about $18 (secondary sources). — [Tailscale docs: Free plans](https://tailscale.com/docs/account/manage-plans/free-plans-discounts.md); [Tailscale pricing](https://tailscale.com/pricing/); [Activepieces summary 2026](https://www.activepieces.com/blog/tailscale-pricing-plans-costs-and-features-2026) [verified via search snippet; the commercial-use restriction should be checked on the official FAQ]
  - **DERP sees only WireGuard ciphertext**, and relay traffic is end-to-end encrypted. — [Tailscale KB: DERP servers](https://tailscale.com/kb/1232/derp-servers) [bg]
  - **Trust caveat**: the coordination server distributes node public keys and could in principle inject a foreign node. **Tailnet Lock** counters this: node keys must be signed by trusted local devices. — [Tailscale KB: Tailnet Lock](https://tailscale.com/kb/1226/tailnet-lock) [bg]
  - **tsnet**: a Go library that embeds a program as its own tailnet node, in userspace without a TUN device. — [Tailscale KB: tsnet](https://tailscale.com/kb/1244/tsnet) [bg]
  - **libtailscale**: a C library wrapping tsnet, intended for embedding in other languages. — [github.com/tailscale/libtailscale](https://github.com/tailscale/libtailscale) [bg; the GitHub fetch returned 504]. Mobile embedding is mainly through community wrappers: Flutter/Dart packages report that on Android, Go's `net.Interfaces()` runs into missing permissions (CAP_NET_ADMIN) and that persistent nodes need API 31+. — [tsnet_flutter](https://pub.dev/documentation/tsnet_flutter/0.3.0); [tailscale.dart](https://pub.dev/documentation/tailscale/0.9.0/) [verified via search snippet; third-party, not official]
  - There is no official npm/Node binding for tsnet, so a Node.js runner would use the OS-level Tailscale client (simplest) or a sidecar. [bg, inference]
- **Headscale**: self-hosted open-source implementation of the Tailscale coordination server (BSD-3), designed for a single tailnet. — [github.com/juanfont/headscale](https://github.com/juanfont/headscale) [bg]. The official Tailscale iOS app can be pointed at Headscale from version 1.38.1 via "alternate coordination server". — [Headscale docs: iOS client](https://www.github.com/juanfont/headscale/blob/main/docs/iOS-client.md) [verified via search snippet]. Android can be configured with a custom server too. [bg] You can run your own DERP server on the VPS (Headscale has an embedded DERP server). [bg]
- **NetBird**: WireGuard mesh with management, signal and relay servers. Since **v0.53.0 (August 2025)**, management, relay and signal are **AGPLv3**, while the clients remain BSD-3. Versions before 0.53.0 stay BSD-3. A commercial license is available. — [NetBird AGPL announcement](https://netbird.io/knowledge-hub/netbird-agpl-announcement); [v0.53.0 release](https://newreleases.io/project/github/netbirdio/netbird/release/v0.53.0) [verified via search snippet]. AGPL obligations only bite if you modify the server **and** offer it as a service to others (secondary interpretation). — [wz-it.com](https://wz-it.com/en/blog/netbird-self-hosting-license-commercial-starter/)
- **ZeroTier**: own L2/L3 protocol (not WireGuard). Since **v1.16.0 (August 2025)**, core and service are **MPL-2.0** and the network controller is under a commercial source-available license (free for personal and non-profit use, paid for commercial use). The controller is no longer included in the default binaries. Earlier versions were BSL 1.1 from 1.4.2 on, and before that GPLv3. — [ZeroTier changelog v1.16.0](https://docs.zerotier.com/changelog/2025/08/21/zt1-v1.16.0); [ZeroTier blog 1.16](https://www.zerotier.com/?p=6818); [ZeroTier forum](https://discuss.zerotier.com/t/zerotier-1-16-0-self-hosted-controller/28269) [verified via search snippet]
- **Nebula** (Slack/Defined Networking): overlay built on the Noise protocol with its own certificate authority; "lighthouses" handle discovery. Any host can be configured as a relay, and hosts advertise relay support through the lighthouse. — [Defined: Managed Lighthouses / Mobile](https://defined.net/blog/announcing-managed-lighthouses/) [verified via search snippet]. **Mobile Nebula** exists for Android and iOS (v0.10.0 added Always-On, custom DNS and inbound firewall rules). — [Defined docs: Mobile Nebula](https://docs.defined.net/glossary/mobile-nebula/) [verified via search snippet]. License MIT. — [github.com/slackhq/nebula](https://github.com/slackhq/nebula) [bg]
- **iroh (n0)**: **iroh 1.0 released 2026-06-15** after 65 pre-releases, with a stable wire protocol and API. It "dials keys, not IPs": endpoints are addressed by public key (the device key), hole punching runs over QUIC (QUIC multipath, NAT traversal inside QUIC) with fallback to relay servers. — [iroh blog: v1](https://iroh.computer/blog/v1) [verified]
  - Stat: typically "95% of data transferred in a connection" flows directly. The public relays saw more than 200 million endpoints in 30 days. Relay traffic is rate-limited, and the limits can change at any time. Relay binaries are open source and you can run your own. — [iroh blog: v1](https://iroh.computer/blog/v1) [verified]. The claim that about 90% of hole punches succeed comes only from a third-party blog. — [Pinggy](https://pinggy.io/blog/iroh_1_0_dial_keys_not_ips/) [unverified]
  - Official bindings: Rust, **Python, Node.js, Swift, Kotlin**; FFI is back with 1.0; WASM/browser supported. — [iroh blog: v1](https://iroh.computer/blog/v1) [verified]
  - Public relay support for 0.9x and 1.0-rc ended on **2026-09-30**, and for 0.35 it ends on 2026-12-31. 1.0 is supported until end of life. Use 1.x for new projects. — [iroh blog: v1](https://iroh.computer/blog/v1) [verified]
  - rc.1 fixed hole punching when the responder sits behind hard NAT. Before that it only worked when the initiator was the side behind hard NAT. — [iroh 1.0.0-rc.1](https://iroh.computer/blog/iroh-1-0-0-rc-1) [verified via search snippet]
  - License MIT/Apache-2.0 dual. — [github.com/n0-computer/iroh](https://github.com/n0-computer/iroh) [bg; not mentioned in the v1 post]
- **libp2p (js-libp2p)**: modular P2P stack. **Circuit Relay v2** gives limited (time- and data-capped) relay reservations. **DCUtR** coordinates hole punching over an existing relay connection. Success rate about 70% (see above). — [libp2p specs: circuit-v2](https://github.com/libp2p/specs/blob/master/relay/circuit-v2.md); [DCUtR spec](https://github.com/libp2p/specs/blob/master/relay/DCUtR.md); [js-libp2p](https://github.com/libp2p/js-libp2p) [bg for specs; success rate verified]. Inference: Circuit Relay v2 limits are designed for setup, not long-running data transfer, so you would need your own relay without limits. There is no first-class mobile SDK (React Native/browser-like at most).
- **WebRTC data channels**: ICE (STUN/TURN) for NAT traversal, DTLS for transport encryption, SCTP for data channels. Needs a signaling server, which the existing coordinating server can play, plus TURN (e.g. coturn) as relay. TURN relays only DTLS ciphertext. Native on Android/iOS through libwebrtc; on Node, for example, `node-datachannel`. — [RFC 8831 WebRTC Data Channels](https://www.rfc-editor.org/rfc/rfc8831); [RFC 8445 ICE](https://www.rfc-editor.org/rfc/rfc8445); [node-datachannel](https://github.com/murat-dogan/node-datachannel) [bg]. Caveat: the DTLS fingerprints are exchanged through signaling, so a malicious signaling server could mount a MITM unless the fingerprints are bound to the device keys. [inference]
- **Cloudflare Tunnel (cloudflared)**: outbound-only connection from the origin to Cloudflare (QUIC/HTTP2, port 7844). **Cloudflare terminates TLS and sees the plaintext.** No P2P path. — [flaviocopes guide](https://flaviocopes.com/cloudflare-tunnel/); [openprx docs](https://openprx-docs.pages.dev/en/prx/tunnel/cloudflare) [verified via search snippet; third-party, not official Cloudflare docs]. For "the server must not read the content" it only works with additional application-layer E2E. [inference]
- **Plain outbound WebSocket/HTTPS relay through your own server (status quo)**: works behind any NAT, CGNAT or UDP block because it is pure TCP/443 outbound. All traffic runs through the VPS (latency, bandwidth). TLS ends at the server, so confidentiality requires application-layer E2E (see Q2). [inference, consistent with the failure cases in the Tailscale article: networks that block UDP leave only a TCP/HTTPS relay — [Tailscale](https://tailscale.com/blog/how-nat-traversal-works)]

**Battery / mobile**
- iOS/Android VPN apps (Tailscale, WireGuard, NetBird, Mobile Nebula) run as OS VPN extensions (NetworkExtension / VpnService) and need keepalives for NAT mappings. [bg] WireGuard itself is "silent" when idle unless PersistentKeepalive is set. — [WireGuard quickstart](https://www.wireguard.com/quickstart/) [bg]
- I found no reliable, current measurements of battery drain per solution. See Gaps.

### Inferences
- Since about 10–30% of connections cannot be hole-punched (hard NAT on both sides, UDP blocks, mobile CGNAT), every solution needs a relay. For a phone on mobile data, the relay case is realistic, so the relay should run on your own VPS (own DERP / iroh relay / TURN / the existing WS server) so that you are not exposed to rate limits or vendor terms.
- Licenses for a 2-person team: Tailscale clients are BSD-3, Headscale BSD-3, Nebula MIT, iroh MIT/Apache, ZeroTier core MPL (controller restricted for commercial use), NetBird server AGPL (no problem when self-hosted unmodified). Tailscale Personal is for non-commercial use (verify), so a commercial project would need Standard (about $8/user/month) or Headscale.
- The least integration work for an existing Node.js runner system: run Tailscale/Headscale at OS level on PC, laptop, VPS and phone, and have runners/servers talk over the 100.x tailnet IPs. But the phone as a worker cannot easily use the VPN while backgrounded on iOS (see Q3), and you add a second control plane.
- Most elegant at the application level: iroh 1.x embedded in the Node runner and the mobile app (Node/Swift/Kotlin bindings). Device identity is the iroh public key, which can be mapped directly onto the existing device and job model.

### Gaps
- No official, current per-platform success-rate figures from Tailscale, NetBird, ZeroTier or Nebula. Only Tailscale's ">90%" estimate for basic techniques.
- The iroh hole-punch success rate (~90%) is only from a third-party blog; officially there is only "95% of data direct".
- The status of Tailscale "Peer Relays" and its availability in tsnet/libtailscale on mobile could not be verified. The libtailscale GitHub page was unreachable (504).
- No reliable 2026 measurements of battery drain for Tailscale, NetBird, ZeroTier, iroh or WebRTC on Android/iOS.
- The ZeroTier/NetBird mobile apps and their self-hosting support on iOS were not checked in detail.

## Q2: End-to-end encryption so the coordinating server cannot read prompts and results

### Takeaway
The VPN/overlay layer (WireGuard/Noise, QUIC/TLS in iroh, DTLS in WebRTC) already protects content against relays. But as long as the server also distributes the keys, it can theoretically slip in its own key (MITM). The fix is out-of-band device pairing (a QR code containing the public key plus a fingerprint), with only paired device keys accepted. With the existing server-relay design, application-layer E2E is enough: a libsodium sealed box or `crypto_box` per job, or better a Noise session (IK/XX) per device pair. MLS is overkill for 2–5 devices.

### Cited Findings
- **libsodium sealed boxes**: the sender creates an ephemeral X25519 key pair per message. Encryption uses `crypto_box` (X25519 + XSalsa20-Poly1305), and the nonce is BLAKE2b(ephemeral pk ‖ recipient pk). Only the recipient can decrypt, and integrity is checked. **No sender authentication**: the recipient does not know who sent the message. The sender cannot decrypt afterwards. Overhead is `crypto_box_SEALBYTES` (ephemeral public key plus MAC). — [libsodium: Sealed boxes](https://doc.libsodium.org/public-key_cryptography/sealed_boxes) [verified]
  - Inference: the lack of forward secrecy and sender authentication means sealed boxes alone are not enough for jobs. Use authenticated `crypto_box` (sender sk + recipient pk), or sign the sealed payload with the device's Ed25519 key. — [libsodium: Authenticated encryption](https://doc.libsodium.org/public-key_cryptography/authenticated_encryption) [bg]
- **Noise Protocol Framework**: handshake patterns such as `IK` (initiator knows the responder's static key, e.g. from QR pairing) and `XX` (mutual exchange of static keys), with DH, AEAD and hash chosen freely, plus forward secrecy through ephemeral keys. WireGuard uses `Noise_IKpsk2`. — [Noise spec](https://noiseprotocol.org/noise.html); [WireGuard protocol](https://www.wireguard.com/protocol/) [bg]
- **Nebula** also builds on Noise, with its own CA certificates per host. — [github.com/slackhq/nebula](https://github.com/slackhq/nebula) [bg]
- **iroh**: connections are secured by the device key, and identity, permissions and attribution build on that key. Dialing is by public key, not IP. — [iroh blog: v1](https://iroh.computer/blog/v1) [verified]. Technically: QUIC with TLS 1.3 and raw public keys (Ed25519), so relays only forward encrypted QUIC packets. — [iroh docs](https://www.iroh.computer/docs) [bg]
- **Tailscale/DERP**: relays forward WireGuard-encrypted packets routed by public key, and the relay cannot read the content. — [Tailscale: How NAT traversal works](https://tailscale.com/blog/how-nat-traversal-works) [verified]. The coordination server distributes keys, and **Tailnet Lock** requires node keys to be signed by trusted local nodes, which protects against key injection by the control server. — [Tailscale KB: Tailnet Lock](https://tailscale.com/kb/1226/tailnet-lock) [bg]
- **MLS (RFC 9420)**: group key exchange with forward secrecy and post-compromise security, efficient for large groups (tree-based). — [RFC 9420](https://www.rfc-editor.org/rfc/rfc9420) [bg]. Inference: for a "device group" of 2–6 devices, pairwise Noise or crypto_box sessions are simpler. MLS only pays off with many devices or members and frequent group changes.
- **Key verification / pairing**: the pattern from Signal-style safety numbers and WhatsApp QR codes, i.e. comparing fingerprints of the public keys out-of-band. — [Signal: Safety numbers](https://support.signal.org/hc/en-us/articles/360007060632-What-is-a-safety-number-and-why-do-I-see-that-it-changed) [bg]

### Inferences
- Concrete design: every device (phone, PC, laptop, VPS-runner) creates an Ed25519/X25519 key pair locally on first start and stores it in the Android Keystore / iOS Keychain / OS keyring. Pairing: the home PC shows a QR code `{deviceId, X25519-pk, Ed25519-pk, server-url, one-time pairing secret}`, and the phone scans it. Both store each other's public key ("trusted device list"), signed by the user's first device, which is similar in spirit to Tailnet Lock. The server only stores public keys and routing metadata.
- Job payload: `{jobId, capability, model, dataClass}` stays in plaintext for routing. Prompt and attachments go in `crypto_box(sender_sk, recipient_pk)` or a Noise session. The result comes back encrypted the same way. Metadata (size, timing, model choice) remains visible to the server. That is acceptable but should be documented.
- If transport is iroh or Tailscale, the transport is already E2E between device keys. You still need application-layer E2E if the job sometimes takes the server-relay path (e.g. the existing WS) or is buffered in the queue.
- Forward secrecy: sealed box and static `crypto_box` give none. Noise IK/XX with ephemeral keys does. For "private" data, Noise (e.g. via `noise-protocol`/`@chainsafe/libp2p-noise` in Node, or libsodium `crypto_kx` + `secretstream` for session keys) is preferable. — [libsodium key exchange](https://doc.libsodium.org/key_exchange) [bg]

### Gaps
- No independent security audit of iroh 1.0 or of Headscale was found in this session.
- No source checked on the cryptographic details of iroh (TLS 1.3 raw public keys, Ed25519). Marked [bg].
- Whether Tailnet Lock works with Headscale was not checked.

## Q3: Mobile background constraints (phone as client or occasional worker; FCM/APNs wake-ups)

### Takeaway
A phone can reliably act as a **client** (sends a job, waits for or polls the result in the foreground, or gets a notification when it's done). As a **worker**, it is only realistic in the foreground or while charging. Silent pushes on iOS are rate-limited and not guaranteed. On Android, high-priority FCM messages without a visible notification can be deprioritized. Design: the phone never has to be reachable; it always connects outbound. Push only signals "result ready" or "job for you", and the data is fetched afterwards.

### Cited Findings
- **FCM (Android)**: normal-priority messages are delayed in Doze until the device wakes. High-priority messages are delivered immediately and can wake the device. High priority is meant for time-sensitive, **user-visible** content. High-priority messages that don't lead to a visible notification can be **deprioritized**. The FCM Aggregate Delivery Data API shows the deprioritized share. — [Firebase: Set and manage Android message priority](https://firebase.google.com/docs/cloud-messaging/android-message-priority); [Firebase blog 2025: FCM on Android](https://firebase.blog/posts/2025/04/fcm-on-android) [verified via search snippet]
- **APNs (iOS) background push**: `content-available: 1`, header `apns-push-type: background`, `apns-priority: 5`. The system throttles background pushes (Apple's guidance is to send them sparingly, often quoted as "no more than two or three per hour"). Delivery is not guaranteed, and the app gets about 30 seconds of runtime. — [Apple: Pushing background updates to your app](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app) [**bg**: the page did not render in the fetch, so these are not verbatim quotes. The "2–3/hour" figure and the 30 s window must be checked on the live page]
- iOS VPN apps (Tailscale and others) run as a NetworkExtension and stay connected in the background, but your own app's process is not kept alive by that. [bg, inference] — [Apple NetworkExtension](https://developer.apple.com/documentation/networkextension) [bg]
- Android: long-running work needs a foreground service with a visible notification, and Android 14+ requires declared foreground service types. — [Android: Foreground service types](https://developer.android.com/develop/background-work/services/fg-service-types) [bg]

### Inferences
- The phone as **client**: send the job over WS/iroh while the app is in the foreground. If the user closes the app, the result stays on the server (encrypted for the phone's key) or on the home PC. Notify with an FCM/APNs **visible** alert ("Your answer is ready"), never with the content. The push payload holds only the jobId, because Apple/Google would otherwise see it.
- The phone as **worker**: only advertise the capability when `charging && wifi && app foreground/FGS`. On Android, a foreground service of type `dataSync`/`specialUse` is possible; on iOS, essentially only the foreground (or BGProcessingTask, which is opportunistic, often overnight while charging). The scheduler should treat phone workers as "best effort, lease-based" (heartbeat, short lease, automatic requeue).
- Battery: keep a persistent WS or QUIC connection only in the foreground. In the background, rely on push only (FCM/APNs already keep a system-wide socket, and your own keepalives cost extra).

### Gaps
- Apple's exact current throttling limits (2026) could not be verified from the primary source (rendering failed).
- No measurements found of battery cost for a persistent iroh/WS/Tailscale connection on mobile.
- iOS 26/Android 16-specific changes to background limits were not checked.

## Q4: Serving local models on the home PC and securing that

### Takeaway
Ollama (default port 11434), llama.cpp `llama-server`, LM Studio and vLLM all offer OpenAI-compatible HTTP APIs. **Rule: bind to 127.0.0.1 and have only the local runner talk to it.** Never expose 0.0.0.0 or the port on the LAN or internet. Ollama has no built-in authentication. There are tens of thousands to 175,000 exposed instances being abused for "compute theft". The `--api-key` options in llama-server and vLLM are only one layer and in vLLM do not cover every endpoint.

### Cited Findings
- **Ollama** binds to localhost by default. The risk only appears when `OLLAMA_HOST=0.0.0.0` is set or the port is mapped in Docker. Ollama has **no built-in authentication**. — [UpGuard: Securing exposed Ollama instances](https://www.upguard.com/blog/understanding-and-securing-exposed-ollama-instances); [Ollama FAQ](https://github.com/ollama/ollama/blob/main/docs/faq.md) [verified via search snippet / FAQ bg]
- Exposure figures: Cisco Talos (September 2025) found more than 1,100 exposed Ollama servers, about 20% of them with models susceptible to unauthorized access. — [Cisco blog](https://blogs.cisco.com/?p=477366) [verified via search snippet]. A Shodan query in April 2026 reportedly returned more than 25,000. — [insecurestack](https://insecurestack.substack.com/p/eus-exposed-ai-infrastructure). About 175,000 exposed instances in 130 countries (SentinelLabs/Censys, cited secondhand), with abuse ("Operation Bizarre Bazaar", reselling GPU compute) and about half having tool-calling enabled. — [Twingate](https://www.twingate.com/blog/ollama-server-exposure); [Elest.io](https://blog.elest.io/175-000-ollama-servers-are-wide-open-right-now-is-yours-one-of-them/) [secondary sources, primary report not checked; the figures conflict, partly because of different points in time]
- **llama.cpp `llama-server`**: default `--host 127.0.0.1` (use `0.0.0.0` for external access). `--api-key` accepts several comma-separated keys, and `--api-key-file` is also available. OpenAI-compatible endpoints under `/v1`. — [llama-server docs (Mintlify mirror)](https://www.mintlify.com/ggml-org/llama.cpp/api/tools/llama-server); [upstream README](https://github.com/ggml-org/llama.cpp/tree/master/tools/server) [mirror verified via search snippet; upstream bg]

## Q5: Recommended minimal architecture for a 2-person team (outbound runners, job dispatch, capability routing, data class "private")

### Takeaway
Keep the existing design (runners connect outbound over WSS to the coordinating server) and add three layers: (1) **device identity + QR pairing** (Ed25519/X25519 per device, trusted device list per user, signed by an existing device); (2) **application-layer E2E** of the job payload (libsodium `crypto_box`/Noise) so the server routes only on metadata; (3) **capability-plus-policy routing** in the scheduler (`dataClass=private` → only devices of the same owner, never third-party or cloud runners). Use direct P2P (iroh 1.x or Tailscale/Headscale) only as an optional fast path for large payloads or streaming. The server relay stays as the fallback that always works (TCP/443).

### Cited Findings (building blocks the recommendation rests on)
- TCP/HTTPS relays work even where UDP is blocked; hole punching fails with hard NAT on both sides and with CGNAT. — [Tailscale](https://tailscale.com/blog/how-nat-traversal-works) [verified]
- Hole punching only succeeds about 70% (libp2p) to >90% (Tailscale basic) of the time, so a relay is always needed. — [arXiv 2510.27500](https://arxiv.org/html/2510.27500v1); [Tailscale](https://tailscale.com/blog/how-nat-traversal-works) [verified]
- iroh 1.0: key-based dialing, Node.js/Swift/Kotlin bindings, self-hostable relays, ~95% of data direct. — [iroh blog: v1](https://iroh.computer/blog/v1) [verified]
- Sealed boxes do not authenticate the sender, so use authenticated `crypto_box` or a signature. — [libsodium](https://doc.libsodium.org/public-key_cryptography/sealed_boxes) [verified]
- Model servers stay on localhost, because Ollama has no authentication and vLLM's `--api-key` is incomplete. — [UpGuard](https://www.upguard.com/blog/understanding-and-securing-exposed-ollama-instances); [vLLM security](https://docs.vllm.ai/en/latest/usage/security.html) [verified via search snippet]
- Push wake-ups are unreliable or throttled, so treat the phone as a best-effort worker. — [Firebase priority](https://firebase.google.com/docs/cloud-messaging/android-message-priority) [verified]; [Apple background updates](https://developer.apple.com/documentation/usernotifications/pushing-background-updates-to-your-app) [bg]

### Inferences (recommendation)

**Phase 1 (minimal, ~days of work): server relay + app-layer E2E**
1. `devices` table: `{deviceId, ownerUserId, ed25519Pub, x25519Pub, kind: phone|pc|laptop|vps, addedBy(deviceId), addedSig, revokedAt}`. Private keys stay on the device (Keystore/Keychain/OS keyring). Never on the server.
2. Pairing: an existing device (e.g. the home PC) shows a QR code with a one-time token plus its public key. The new device scans it, sends its own public key through the server, and the existing device signs it ("device certificate"). Show a fingerprint on both screens as a short code (e.g. 6 words or digits) for comparison. Revocation works through a signed revoke entry.
3. Runner registration (outbound WSS, as today) sends `capabilities`: `{models:[{name, quant, ctx, vramGB}], gpu, ramGB, battery?, charging?, network: wifi|cellular, trustDomain: own|team|cloud}` plus a heartbeat/lease.
4. Job: `{jobId, ownerUserId, requiredCapability:{model|minVram|family}, dataClass: public|team|private, recipientDeviceIds[], ciphertext, senderDeviceId, sig}`. The client picks the target device or a candidate list from the capability index the server publishes. With several candidates, encrypt once per recipient (multi-recipient: random content key, wrapped per device key).
5. Scheduler policy (enforced on the server, verified again on the runner): `dataClass=private` → only `device.ownerUserId == job.ownerUserId && trustDomain=='own'`. The runner also refuses to decrypt if the sender's device key is not in its local trust list (defense in depth, so a compromised server cannot fake a job).
6. The runner decrypts, calls `127.0.0.1` Ollama/llama-server, encrypts the result for `senderDeviceId`, and streams chunks encrypted (Noise transport or libsodium `secretstream`) through the existing WS connection.
7. Phone: client mode by default. After job completion the server sends a visible FCM/APNs notification containing only the jobId. Worker mode only when the app is in the foreground and charging, with short leases.

**Phase 2 (optional): direct path for latency and bandwidth**
- Option A, the lowest code effort: **Tailscale** (Personal 6 users, free, non-commercial; otherwise Standard) or **Headscale** on the VPS (BSD-3, own DERP). Runner and server talk over tailnet IPs. Enable Tailnet Lock (Tailscale). Downside: a second identity system next to your own device keys, and the iOS app as client only.
- Option B, the best integration: **iroh 1.x** in the Node runner and the mobile app, with your own iroh relay on the VPS (avoids rate limits on the public n0 relays). The iroh endpoint ID can be the device's Ed25519 key or be bound to it by signature. The coordinating server distributes endpoint addresses (signaling); data flows directly or through your own relay.
- Not recommended for "private": Cloudflare Tunnel (TLS is terminated at Cloudflare) unless app-layer E2E is used anyway; ZeroTier (controller license restricted for commercial use); libp2p (more complex, 70% hole punching, relay v2 limited, no good mobile SDK).

**Why this suits a 2-person team**
- No new infrastructure dependency in Phase 1, and it reuses the existing outbound-runner design.
- No open port at home; only the VPS has 443 open (as today).
- The server becomes "honest-but-curious-proof": it sees the routing metadata, but not prompts or results. A malicious server cannot inject fake devices without detection if trust lists are signed on the client side.

### Gaps
- No real-world reports found on combining your own job queue with iroh in Node.js (maturity of the Node bindings, streaming throughput).
- Not checked: multi-recipient encryption libraries for JS (e.g. age/`@noble`/libsodium wrappers) and their mobile equivalents.
- The legal question of whether Tailscale Personal is enough for the team's use case (commercial or not) depends on the project and was not clarified.
